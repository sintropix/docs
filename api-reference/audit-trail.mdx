The audit trail is a forensic, append-only log of every mutating request against an Organization's data. Each row stores the actor, credential type, declared actor, request id, route, method, and a diff of what changed. GET requests do not produce audit records.

The trail belongs to the Organization. You read it in three ways:

- The **Log** of the Organization, every write to any of its Entities and to the data the Organization shares, filtered by Entity if you like: [`GET /api/organizations/:organizationId/audit-trail`](#list-the-organization-log).
- The **Actividad** of one record, its own history: [`GET /api/entities/:entityId/audit-trail`](#list-the-history-of-one-record).
- The **Audit Trail Feed**, every new envelope of the Organization as it lands, oldest first: [`GET /api/organizations/:organizationId/audit-trail/feed`](#follow-the-audit-trail-feed).

All three routes need `books` read in the Organization. An [Email Arrival](#email-arrivals) shows to every reader, but only a reader who can [read email](/api-reference/integrations#who-can-read-email) sees its sender, recipients, and subject. The first two return the same [page shape](#response). The feed returns its own [feed page](#feed-response).

## List the Organization Log

`GET /api/organizations/:organizationId/audit-trail`

Returns a paginated page of the Organization's audit envelopes, plus the named resources needed to render them without extra lookups. Writes that belong to no Organization never appear.

With no filter, the page lists every envelope of the Organization. That includes the envelopes of Organization routes that name no Entity, such as a [Partner merge](/api-reference/partners#merge-partners) or a [Dimension](/api-reference/dimensions) change. Those have `entityId` set to `null`, and the app labels them **Empresa**.

**Query params**

| Param | Type | Required | Description |
| --- | --- | --- | --- |
| `entityIds` | UUID | No | Keep the envelopes of this Entity. Repeat the param for several Entities, up to 100. |
| `includeOrganizationEnvelopes` | boolean | No | `true` keeps the envelopes that name no Entity (**Empresa**). Defaults to `false`. |
| `cursor` | integer | No | Page cursor (positive integer). Pass the `nextCursor` from the previous page to fetch the next one. |
| `limit` | integer | No | Page size, 1 to 100. Defaults to 50. |
| `from` | day or instant | No | Keep envelopes at or after this bound. A day starts at its midnight. See [Date range](#date-range). Must not be after `to` when both are given. |
| `to` | day or instant | No | Keep envelopes at or before this bound. A day includes the whole day. See [Date range](#date-range). |
| `actorUserId` | UUID | No | Filter to a specific user. |

**How the Entity filter matches**

Send `entityIds`, `includeOrganizationEnvelopes`, or both, to narrow the Log:

- An envelope matches an Entity when it names that Entity, or when it changes a row of that Entity. For example, a Partner merge names no Entity, but it shows under each Entity whose rows it changed.
- Inside a matched envelope, the changes to rows of Entities you didn't select are hidden. Changes to rows the whole Organization shares, such as a Partner, always show.
- A row that moved between two Entities shows under both.
- With `includeOrganizationEnvelopes=true`, the envelopes that name no Entity also match.

Selecting every Entity plus **Empresa** gives the same Log as no filter.

An API key [confined to one Entity](/guides/api-keys) reads its own Entity and the **Empresa** envelopes by default. Asking for another Entity in `entityIds` answers `404` with `ENTITY_NOT_FOUND_ERROR`.

```bash
curl -s "https://api.sintropix.com/api/organizations/$ORGANIZATION_ID/audit-trail?entityIds=$ENTITY_ID&includeOrganizationEnvelopes=true&limit=50" \
  -H "x-api-key: $SINTROPIX_API_KEY"
```

## List the history of one record

`GET /api/entities/:entityId/audit-trail`

Returns the audit envelopes that changed one row of the Entity, the same history the **Actividad** tab of a record shows in the app. An envelope never shows a change to another Entity's rows.

**Query params**

| Param | Type | Required | Description |
| --- | --- | --- | --- |
| `tableName` | string | Yes | The table of the row. See accepted values below. |
| `rowId` | UUID | Yes | The id of the row. |
| `cursor` | integer | No | Page cursor (positive integer). Pass the `nextCursor` from the previous page to fetch the next one. |
| `limit` | integer | No | Page size, 1 to 100. Defaults to 50. |
| `from` | day or instant | No | Keep envelopes at or after this bound. A day starts at its midnight. See [Date range](#date-range). Must not be after `to` when both are given. |
| `to` | day or instant | No | Keep envelopes at or before this bound. A day includes the whole day. See [Date range](#date-range). |
| `actorUserId` | UUID | No | Filter to a specific user. |

**Accepted `tableName` values**

The trail records changes to the tables of the books and the records around them, for example `ledger_entry`, `ledger_entry_line`, `ledger_entry_line_dimension_value`, `invoice`, `invoice_attachment`, `attachment`, `partner`, `partner_alias`, `partner_bank_details`, `entity_partner`, `bank_movement`, `bank_movement_attachment`, `bank_account`, `reconciliation_allocation`, `fixed_asset`, `fixed_asset_class`, `fixed_asset_depreciation_entry`, `intercompany_link`, `expense_claim`, and `task`. Any string is accepted; one that names no audited row matches nothing.

Some parents also pull in their child rows: `tableName=ledger_entry` returns changes to that entry, to its `ledger_entry_line` rows, and to the Dimension tags of those lines (`ledger_entry_line_dimension_value`); `tableName=invoice` returns changes to that invoice and to its `invoice_attachment` links; `tableName=bank_movement` returns changes to that movement and to its `bank_movement_attachment` links; `tableName=partner` returns changes to that Partner, its `partner_alias` rows, its `entity_partner` links, and the Partners merged into it. The invoice and bank movement histories also carry the `attachment` rows of the files linked in the same request. For `tableName=partner_bank_details`, pass the Partner's id as `rowId`. For an [Expense Rendition](/api-reference/expense-claims), `tableName=invoice` also returns the history of the Expense Claim it came from: who submitted it and who approved it.

### Dimension tags in the history of an Entry

A tag row names its line and its Value, so its `before` and `after` images carry `line_id` and `dimension_value_id`. The Entry's history includes the tags written when the entry is booked and every later [retag of a line](/api-reference/ledger-entries#put-/api/entities/entityid/ledger/lines/lineid/dimension-values). It also includes the tag a line drops when you reclassify it to a balance account, and the tags of a line the entry no longer holds.

A retag replaces the line's tags, so it shows as a `delete` of each old tag and an `insert` of each new one, in one envelope. To read a retag as a change of Value, pair the `delete` and the `insert` of the same `line_id` and Dimension. The **Actividad** tab of the Entry reads it that way, for example *Centro de costo — 4010 Ventas: VEN Ventas → OPS Operaciones*. A retag that writes back the same tags shows no item there.

```bash
curl -s "https://api.sintropix.com/api/entities/$ENTITY_ID/audit-trail?tableName=invoice&rowId=$INVOICE_ID" \
  -H "x-api-key: $SINTROPIX_API_KEY"
```

## Date range

Both routes take the same `from` and `to` bounds. Each bound is one of two forms:

- **A day**, as `YYYY-MM-DD`, for example `2026-11-10`. A day is the whole day on the Organization's calendar, in the America/Santiago time zone. `from` starts at that day's midnight. `to` ends at the next midnight, so it keeps the whole day.
- **An instant with an offset**, for example `2026-11-10T00:30:00-03:00` or `2026-11-10T03:30:00Z`. An instant is that exact moment, and the range includes it.

So `from=2026-11-10&to=2026-11-10` returns every envelope of November 10 in Santiago. You can mix the forms, for example `from=2026-11-10&to=2026-11-10T12:00:00-03:00`.

When either bound is a day, the two bounds are compared by their day in Santiago, and `from` must not fall on a later day than `to`. When both are instants, `from` must not be after `to`.

The routes answer `400` for:

- an instant with no offset, such as `2026-11-10T00:30:00`
- a day that doesn't exist, such as `2026-02-30`
- any other value, such as `yesterday`
- a `from` after `to`

The error message names both accepted forms: `Expected a day (YYYY-MM-DD) or an instant with an offset (2026-11-10T00:30:00-03:00)`.

```bash
curl -s "https://api.sintropix.com/api/organizations/$ORGANIZATION_ID/audit-trail?from=2026-11-10&to=2026-11-10" \
  -H "x-api-key: $SINTROPIX_API_KEY"
```

## Response

Both routes answer `200` with this page:

| Field | Type | Description |
| --- | --- | --- |
| `envelopes` | array | One envelope per mutating request, newest first. See below. |
| `namedResources` | object | Display facts for the resources the envelopes on this page reference. See below. |
| `nextCursor` | integer or `null` | Cursor for the next page, or `null` on the last page. |

Each **envelope**:

| Field | Type | Description |
| --- | --- | --- |
| `id` | integer | Envelope id. |
| `occurredAt` | ISO datetime | When the request was processed. |
| `requestId` | string | Server-generated unique id for the request. |
| `actorUserId` | UUID or `null` | The authenticated user, when there was one. |
| `actor` | object or `null` | `{ id, name, role, deleted }` of the authenticated user, as they were at the write. `role` is the user's Membership Role in the Organization of the write (`staff`, `client`, or `viewer`), or `null` when they held no Membership there. `deleted` is `true` when a Superadmin has [deleted the user](/api-reference/onboarding#delete-/onboarding/users/userid) since. |
| `credentialType` | enum | `session`, `api_key`, `oauth`, or `system`. `oauth` marks a write made by a [connected app](/guides/connected-apps) with an OAuth access token. |
| `apiKeyId` | UUID or `null` | The API key used, for `api_key` requests. |
| `connectedAppClientId` | string or `null` | The OAuth `client_id` of the connected app, for `oauth` requests. |
| `connectedAppName` | string or `null` | The name the connected app declared for itself, as it read at the time of the write, for `oauth` requests. |
| `declaredActor` | string or `null` | Value of the `x-audit-actor` header on API-key mutations. On a change made by Sintropix itself, the part of Sintropix that made it, such as `bank-feed` for a [background job](#background-jobs). |
| `declaredReason` | string or `null` | Value of the `x-audit-reason` header (trimmed) explaining why the change was made. Required on API-key and OAuth-token mutations; optional on browser sessions. `null` on rows written before the header existed. |
| `declaredTrigger` | `slack` \| `app` \| `chat` \| `terminal` \| `main` \| `schedule` \| `null` | Value of the `x-audit-trigger` header: what started the agent turn behind the write. `main` means Erwin started it on his own, from a timer, a notice, or a routine. `slack`, `app`, `chat`, and `terminal` name where a person's message started it. `schedule` appears only on older rows, written when one of Erwin's former schedules started the turn. A request can no longer send it. On a change made by a [background job](#background-jobs), the run that made it, as `<route>@<start instant>`. `null` when the request sent no trigger, on other changes made by Sintropix itself, and on rows written before the header existed. |
| `route` | string | The endpoint pattern that produced the mutation. For a change made by a scheduled job, the job's name. See [Background jobs](#background-jobs). |
| `method` | string | HTTP method, for example `POST`. `JOB` for a change made by a scheduled job. Older rows of the Source Feed sync show `CRON`. |
| `params` | object | Path parameters of the request. |
| `organizationId` | UUID or `null` | The Organization of the write. |
| `entityId` | UUID or `null` | The entity scope of the change. |
| `ipAddress` | string or `null` | IP address of the client that sent the request, not of a proxy in between. An IPv6 address is written in full, with each group padded to four digits, for example `2800:0150:011e:1a00:1c8f:6d2a:3b4e:9f01`. |
| `userAgent` | string or `null` | Caller user agent. |
| `changes` | array | One change per affected row. See below. |

Each **change**:

| Field | Type | Description |
| --- | --- | --- |
| `id` | integer | Change id. |
| `envelopeId` | integer | The envelope this change belongs to. |
| `occurredAt` | ISO datetime | When the row changed. |
| `tableName` | string | One of the table names listed above. |
| `rowPrimaryKey` | object | Primary key of the affected row, for example `{ "id": "..." }`. |
| `operation` | enum | `insert`, `update`, or `delete`. |
| `before` | object or `null` | Row image before the change. `null` on insert. |
| `after` | object or `null` | Row image after the change. `null` on delete. |

Keys inside `before`, `after`, and `rowPrimaryKey` are the stored column names in `snake_case` (for example `entry_date`, `partner_id`), not the camelCase names used elsewhere in the API.

**`namedResources`** carries the display facts of exactly the resources the page's envelopes point at, so a feed can render names without further lookups:

| Field | Type | Description |
| --- | --- | --- |
| `ledgerAccounts` | array | `{ id, code, name }` |
| `partners` | array | `{ id, name }` |
| `bankAccounts` | array | `{ id, name, currency }` where `currency` is an ISO 4217 code. |
| `sources` | array | `{ id, name }` |
| `ledgerEntryLines` | array | `{ id, accountName, entryMemo, entryDate }` where `entryMemo` may be `null` and `entryDate` is `YYYY-MM-DD`. |
| `dimensionValues` | array | `{ id, code, name, dimensionName }` of each [Dimension Value](/api-reference/dimensions) the changes point at, where `dimensionName` is the name of the Value's Dimension. |

A resource that no longer exists is absent from these lists; treat an id you cannot resolve as unknown.

## Follow the Audit Trail feed

`GET /api/organizations/:organizationId/audit-trail/feed`

The **Audit Trail Feed** lets you follow the Organization's trail forward, so your integration or agent can react to what happens instead of polling every list. Each read returns the envelopes written after a cursor, oldest first, and the cursor to read from next. Each change in the feed carries its [Audit Meaning](#audit-meanings): what the change states, such as `bank_movement.booked`.

The feed never skips an envelope and never repeats one. An envelope appears only once every write that started before it has finished, so an envelope from a slow write shows up late rather than never. The feed can lag a write by a moment for that reason.

An API key [confined to one Entity](/guides/api-keys) reads the envelopes of its own Entity and the **Empresa** envelopes, as in the [Log](#list-the-organization-log). Any other caller reads every envelope of the Organization.

<Note>
  Changes written before the feed existed are not in it. Read them with the [Organization Log](#list-the-organization-log).
</Note>

**Query params**

| Param | Type | Required | Description |
| --- | --- | --- | --- |
| `after` | string | No | The cursor to read after: the `nextCursor` of your previous read. Treat it as opaque. Omit it on your first read: the feed answers at once with no envelopes and the cursor of now. |
| `waitSeconds` | integer | No | How long to hold the read open when nothing new is there, 0 to 30. The feed answers as soon as an envelope arrives, or with an empty page when the wait runs out. Defaults to `0`, which answers at once. |
| `limit` | integer | No | Most envelopes per page, 1 to 100. Defaults to 50. |

**How to follow the feed**

1. Call the feed with no `after`. Keep the `nextCursor` it returns.
2. Call it again with `after=<nextCursor>` and a `waitSeconds`, for example `30`.
3. Handle the envelopes on the page, then repeat step 2 with the new `nextCursor`. Every page carries one, empty pages included.

Store the last `nextCursor` you handled. After a restart, resume from it and you receive every envelope you missed, with no gap and no repeat.

```bash
curl -s "https://api.sintropix.com/api/organizations/$ORGANIZATION_ID/audit-trail/feed?after=$CURSOR&waitSeconds=30&limit=100" \
  -H "x-api-key: $SINTROPIX_API_KEY"
```

### Feed response

The feed answers `200` with this page:

| Field | Type | Description |
| --- | --- | --- |
| `envelopes` | array | The envelopes after the cursor, oldest first. Empty when nothing new arrived. Each envelope has the [envelope fields](#response) of the Log. |
| `nextCursor` | string | The `after` of your next read. Always present. |

The feed page has no `namedResources`. Each change in a feed envelope has the [change fields](#response) of the Log, plus:

| Field | Type | Description |
| --- | --- | --- |
| `meaning` | string or `null` | The [Audit Meaning](#audit-meanings) of the change, `<subject>.<act>`. `null` only for a table the trail no longer records. |

### Audit Meanings

An **Audit Meaning** names what a change states about a record, as `<subject>.<act>`. Use it to react to a kind of event without reading the `before` and `after` images yourself.

| Subject | Acts | When |
| --- | --- | --- |
| `bank_movement` | `created`, `updated`, `deleted`, `booked`, `unbooked`, `excluded`, `included`, `assigned`, `unassigned` | `booked` and `unbooked` when the Movement is linked to or unlinked from its Ledger Entry. `excluded` and `included` when it is [excluded from the books](/api-reference/bank-movements#exclude-a-movement-from-the-books) or included again. `assigned` and `unassigned` for an [Assign or Unassign](/api-reference/bank-movements#overpayments-and-the-suspense-account) of its Suspense line. |
| `invoice` | `created`, `updated`, `deleted`, `booked`, `unbooked`, `excluded`, `included` | `booked` and `unbooked` when the Invoice is linked to or unlinked from its booking Entry. `excluded` and `included` when it is excluded from the books or included again. |
| `allocation` | `created`, `updated`, `deleted` | A change to a `reconciliation_allocation` row. |
| `email_arrival` | `created` | An email arrived at a Gmail, Outlook, or Mailbox Integration. See [Email Arrivals](#email-arrivals). |
| Any other recorded table, for example `partner` or `ledger_entry` | `created`, `updated`, `deleted` | An `insert`, `update`, or `delete` of the row. |

A few rules decide the act:

- When one update both books and edits a field, it reads `booked` or `unbooked`. An update that excludes or includes reads `excluded` or `included`. Only an update that does neither reads `updated`.
- `bank_movement.assigned` and `bank_movement.unassigned` sit on a change whose `tableName` is `ledger_entry_line`: the Suspense line of the Movement's Ledger Entry. Assign shrinks or removes that line, and Unassign grows it or brings it back. The Suspense line that a Match creates with the booking reads `ledger_entry_line.created`, not `unassigned`.
- Every other `ledger_entry_line` change reads `ledger_entry_line.created`, `ledger_entry_line.updated`, or `ledger_entry_line.deleted`.

## What the trail captures

The audit trail is row-level and automatic: every write is recorded by the database itself, so no endpoint can skip it. Every mutating request produces one **Audit Envelope** grouping its **Audit Changes**:

- **Actor:** `actorUserId` plus the name and role the authenticated user had at the write. A deleted user keeps that name and role in the trail, and the **Log** shows **(eliminado)** after their name.
- **Credential type:** `session` for browser sessions, `api_key` for API key requests, `system` for changes made by Sintropix itself
- **Declared actor:** the value of the `x-audit-actor` header on API-key mutations (stored as a claim, not a verified identity). Changes Erwin makes while a person chats with him in the app carry `erwin`, with that person as the actor. A [Source Feed](/api-reference/source-feeds#standing-and-tax-period) sync that writes the Standing or Tax Period of a landed DTE carries `source-feed`, credited to the system. An [Email Arrival](#email-arrivals) carries the name of the email Provider that delivered the email, credited to the system. A [background job](#background-jobs) carries the name of the job.
- **Declared reason:** the value of the `x-audit-reason` header (trimmed, up to 500 characters) explaining why the change was made; required on API-key mutations, optional on browser sessions
- **Declared trigger:** the value of the optional `x-audit-trigger` header (stored as a claim), naming what started the agent turn behind the write. Every write Erwin makes carries the trigger of his turn: `main` when he started the work on his own, from a timer, a notice, or a routine, or `slack`, `app`, `chat`, or `terminal` when a person's message there started it. An envelope whose `declaredActor` starts with `erwin` and whose `declaredTrigger` is `main` is a change Erwin made on his own. Older rows show `schedule` for the same case
- **Request id:** a server-generated unique id grouping all changes in one request
- **Route and HTTP method:** the endpoint that produced the mutation, or the background job that made it
- **Entity id:** the entity scope the change occurred within
- **Diff:** for inserts and deletes, the full row image; for updates, only the columns that moved with before and after values

GET requests are not audited. Unbooking (soft delete) is no longer traceless: the removed entry's full image survives as Audit Changes.

### Background jobs

Some changes are made by Sintropix on its own, on a schedule, with no request behind them. Each write of a background job lands in the trail like any other: it shows in the **Log**, in the **Actividad** of the record it changed, and in the [Audit Trail Feed](#follow-the-audit-trail-feed). Its envelope carries:

| Field | Value |
| --- | --- |
| `credentialType` | `system` |
| `actor`, `actorUserId` | `null` |
| `declaredActor` | The job, from the table below |
| `declaredTrigger` | The run, as `<route>@<start instant>`, for example `scheduled-entries-tick@2026-11-09T19:24:26.364Z` |
| `route` | The job's route, from the table below |
| `method` | `JOB` |
| `params` | `{}` |

| Job | `route` | `declaredActor` | The app shows | What it changes |
| --- | --- | --- | --- | --- |
| Scheduled [Bank Feed](/api-reference/bank-feeds) sync | `bank-feed-sync-sweep` | `bank-feed` | **Sincronización bancaria** | The Bank Movements it imports into fed Bank Accounts. |
| Scheduled [Source Feed](/api-reference/source-feeds) sync | `source-feed-sync-sweep` | `source-feed` | **Sincronización de documentos** | The Invoices, DTEs, and Partners it lands, and the [Standing and Tax Period](/api-reference/source-feeds#standing-and-tax-period) of landed DTEs. |
| [Wasabil-requested](/api-reference/source-feeds#wasabil-syncs) Source Feed sync | `source-feed-sync-request` | `source-feed` | **Sincronización de documentos** | The same changes as the scheduled Source Feed sync, for the Feeds of a `wasabil` Integration. |
| [Scheduled Entries](/api-reference/ledger-entries#scheduled-entries) | `scheduled-entries-tick` | `scheduled-entries` | **Asientos programados** | The Scheduled Entries it books when their date arrives. |
| [Overdue Tasks](/api-reference/tasks) | `overdue-tasks-tick` | `overdue-tasks` | **Tareas vencidas** | The `task_overdue` [Notifications](/api-reference/notifications#task-notifications) it sends. |
| Automations | `automation-run-sweep` | `automation-runs` | **Automatizaciones** | The Runs that an Automation's schedule starts, and their final status. |

A run that writes for several Organizations opens a separate envelope for each write, and each envelope belongs to one Organization only. So you see only your own Organization's changes. Every envelope of one run carries the same `declaredTrigger`: group on it to read a run as one.

A booking from a vendor's [Booking Template](/api-reference/partners#booking-templates) during the Source Feed sync keeps the `booking-template` declared actor and carries the run's `declaredTrigger`. A sync you [start on demand](/api-reference/source-feeds#post-/source-feeds/sourcefeedid/sync) keeps the route, method, and actor of that request.

<Note>
  Background jobs didn't always write envelopes. Before, only the Source Feed sync's Standing and Tax Period updates and its Booking Template bookings had one, with the method `CRON`. Older changes of the other jobs have no envelope, so they are not in the Log, the Actividad, or the feed.
</Note>

### Email Arrivals

When an email arrives at a Gmail, Outlook, or Mailbox Integration, Sintropix records it as an [Email Arrival](/api-reference/integrations#email-arrivals). Each one is its own envelope, with one `insert` change on the `email_arrival` table whose Audit Meaning is `email_arrival.created`. The Log in the app reads it as **Correo recibido · de** the sender **· asunto** the subject.

| Field | Value |
| --- | --- |
| `credentialType` | `system` |
| `actor`, `actorUserId` | `null` |
| `declaredActor` | The name of the email Provider that delivered the email |
| `method`, `route` | `POST` to the Provider's webhook route, where the Provider told Sintropix of the email |
| `declaredTrigger` | The delivery, as `<route>@<instant>`: the webhook route and when Sintropix received the delivery |
| `entityId` | `null`. An Email Arrival belongs to the Organization, so it shows under **Empresa** |

The change's `after` image holds the Email Arrival's headers in `snake_case`: `integration_id`, `email_id`, `from_address`, `to_addresses`, `subject`, `received_at`, and `attachment_count`. It never holds the body.

The headers are the email's content, so the Log, the feed, and a record's history leave `from_address`, `to_addresses`, and `subject` out of the images for a reader who can't [read email](/api-reference/integrations#who-can-read-email): a `viewer`, or an API key confined to one Entity. That reader sees that an email arrived, and the app's Log reads just **Correo recibido**.
