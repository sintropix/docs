A Source Feed is a recurring pull configured against a [Source](/api-reference/sources). It carries the link date (the start of the window Sintropix imports), the [Integration](/api-reference/integrations) it fetches through, and the [Document Family](#document-families) it lands. Syncing a Feed lands new documents into its Source and keeps the [Standing and Tax Period](#standing-and-tax-period) of the documents it already landed up to date with the SII. Sintropix syncs every Feed on its own every 4 hours, and you can also [sync a Feed on demand](#post-/source-feeds/sourcefeedid/sync). An [expense Feed](#expense-feeds) lands the expenses its tool approved as approved Expense Claims.

## Document families

Every Feed lands one **Document Family**:

| `family` | Documents | Providers that feed it |
| --- | --- | --- |
| `dte` | DTEs: facturas, notas de crédito, boletas, and the other documents of the RCV. | `sii_mirror`, `bsale`, `wasabil` |
| `honorarium` | Boletas de honorarios: the BHE the Entity receives and the BTE it issues. See [Honorarium Feeds](#honorarium-feeds). | `sii_mirror` |
| `expense` | Expense Renditions: the expenses people of the Entity report in an expense tool. See [Expense Feeds](#expense-feeds). | `xpendit` |

An Entity holds at most one Feed of each family, and a Source holds at most one Feed. Two providers of one family describe the same documents, so a second Feed of a family would land them twice. An [Integration](/api-reference/integrations) lists the families its provider can feed in `feedableFamilies`.

An Integration belongs to the Organization, and its Feeds route it to Entities. A Feed lands in the Entity of its route, `/api/entities/:entityId/source-feeds`, and reads through any Integration of that Entity's Organization, even one that already feeds other Entities.

## The Source Feed object

Every route on this page returns Feeds in this shape.

| Field | Type | Description |
| --- | --- | --- |
| `id` | uuid | Feed id. |
| `entityId` | uuid | Owning Entity. |
| `organizationId` | uuid | The Organization of the Entity and the Integration. |
| `sourceId` | uuid | The Source the Feed fills. |
| `integrationId` | uuid | The Integration the Feed reads through. |
| `family` | `dte` \| `honorarium` \| `expense` | The [Document Family](#document-families) the Feed lands. |
| `providerAccountId` | string \| null | For an `expense` Feed, the [Provider Account](#expense-feeds) it reads, such as an Xpendit Subsidiary. `null` for every other family. |
| `feedStartDate` | string (`YYYY-MM-DD`) | The link date: the earliest emission date the Feed imports, on the provider's calendar. |
| `lastSyncedAt` | ISO 8601 timestamp \| null | When the Feed last completed a successful sync. `null` until the first success. |
| `sourceName` | string | Name of the parent Source. |
| `lastSyncRun` | sync run object \| null | The most recent sync, whatever its outcome. `null` until the first sync settles. |
| `createdAt`, `updatedAt` | ISO 8601 timestamp | Row timestamps. |

**Sync run object**

| Field | Type | Description |
| --- | --- | --- |
| `id` | uuid | Run id. |
| `entityId`, `integrationId`, `sourceFeedId`, `sourceId` | uuid | What the run belonged to. |
| `feedStartDate` | string (`YYYY-MM-DD`) | Start of the range the run read. |
| `sweptTo` | string (`YYYY-MM-DD`) | The day the run ran, on the Chilean calendar. Some providers also read documents dated after it; see [The sync window](#the-sync-window). |
| `landedCount` | integer | Documents newly imported. |
| `skippedCount` | integer | Documents already present and unchanged. |
| `ignoredCount` | integer | Documents the run read and did not land, each for a reason. See [Ignored documents](#ignored-documents). |
| `rejectedCount` | integer | Documents refused with a reason. |
| `awaitingCount` | integer | Documents the provider counts but does not list yet, so a later sync lands them. Today only `sii_mirror` boletas; see [SII Mirror boletas](#sii-mirror-boletas). |
| `outcome` | `success` \| `failure` \| `preview` | `preview` when the run was requested with `preview: true`. |
| `failureCode` | string \| null | Error code when `outcome` is `failure` and the failure was a coded rejection. |
| `report` | object | `{ tieOutLines, rejected, ignored?, divergences, updates, tieOutMismatch?, files? }`. `tieOutLines[]` reconcile counts per range (`{ range: { dteTypeCode, taxPeriod, direction: "issued" \| "received" \| null, providerRef, month? }, tracked, count, landed, skipped, ignored, rejected, awaiting }`), where `landed + skipped + ignored + rejected + awaiting` equals `count`. `range.month` (`YYYY-MM`) is present on the tie-out lines of an [expense Feed](#sync-an-expense-feed), one per month of creation. `rejected[]` list refused documents (`{ externalRef, dteTypeCode, folio, reason, detail, document }`, where `reason` is one of `sii_rejected`, `client_rut_missing`, `client_rut_invalid`, `total_off_scale`, `currency_unknown`, `document_invalid`, `currency_mismatch`, `expense_category_unassigned`, or `person_unknown`). An expense Feed's rejections have `dteTypeCode: null` and the expense number as `folio`. `ignored[]` lists the documents the run ignored, each with its reason; see [Ignored documents](#ignored-documents). `divergences[]` list landed documents whose provider copy changed and that the sync left as they are (`{ dteId, externalRef, dteTypeCode, folio, fields: [{ field, landed, provider }] }`, where `field` is one of `total`, `netAmount`, `exemptAmount`, `taxAmount`, `withheldIvaAmount`, `currency`, `issueDate`, `receiverRut`, or `receiverName`). `updates[]` list landed documents whose Standing or Tax Period the sync wrote, in the same shape, where `field` is `standing` or `taxPeriod`, `landed` is the value before, and `provider` the value after; see [Standing and Tax Period](#standing-and-tax-period). `expenseDivergences[]` is present only on an expense Feed's run and lists landed expenses that changed in the tool; see [Changed expenses](#changed-expenses). `tieOutMismatch` is present only when the provider's stated count and the count read disagree. `files` is present only when the Integration's provider carries document files (`sii_mirror` and `xpendit`); see [File attachments](#file-attachments). |
| `occurredAt` | ISO 8601 timestamp | When the run settled. |

## GET `/source-feeds`

List every Source Feed for the Entity, each annotated with its parent Source name.

- **Response:** array of Source Feed objects.

## POST `/source-feeds`

Create a Source Feed. The body names the Source to fill, either an existing one by id or a new one by name, and the response carries both the Feed and that Source.

**Body**

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `id` | uuid | Yes | Client-generated id. Retrying the same `POST` with the same id is rejected instead of creating a duplicate. |
| `integrationId` | uuid | Yes | The Integration to read through: any Integration of the Entity's Organization. Another Organization's answers `404` with `INTEGRATION_NOT_FOUND_ERROR`. |
| `family` | `dte` \| `honorarium` \| `expense` | Yes | The [Document Family](#document-families) to land. It must be one of the Integration's `feedableFamilies`. |
| `providerAccountId` | string | For `expense` only | The id of the [Provider Account](#expense-feeds) to read, from [`GET /integrations/:integrationId/provider-accounts`](/api-reference/integrations#get-/integrations/integrationid/provider-accounts). Required when `family` is `expense`: without it, the request answers `400`. Other families read the whole external account and take none. |
| `feedStartDate` | string (`YYYY-MM-DD`) | Yes | The link date: the earliest emission date to import. |
| `source` | object | Yes | Exactly one of `{ "sourceId": "<uuid>" }` (an existing Source) or `{ "sourceName": "<name>" }` (create a Source with that name). A body carrying both keys is rejected. For an `expense` Feed, an existing Source must hold Expense Renditions, and a Source you create holds them. |

**Response:** `{ feed, source }`, where `feed` is the Source Feed object and `source` is the Source it fills: `{ id, entityId, name, holdsExpenseRenditions, invoiceCount, createdAt, updatedAt }`.

**Domain errors**

| Code | Status | Meaning |
| --- | --- | --- |
| `SOURCE_FEED_FAMILY_NOT_FED_ERROR` | `422` | The Integration's provider doesn't feed this `family`, for example `honorarium` through a `bsale` Integration. `params: { integrationId, family }`. |
| `SOURCE_FEED_FAMILY_ALREADY_FED_ERROR` | `409` | The Entity already has a Feed of this `family`. Delete it first. `params: { entityId, family }`. |
| `SOURCE_FEED_SOURCE_ALREADY_FED_ERROR` | `409` | The Source already has a Feed. `params: { sourceId }`. |
| `SOURCE_FEED_ALREADY_EXISTS_ERROR` | `409` | A Feed with this `id` already exists, for example on a retried `POST`. `params: { sourceFeedId }`. |
| `SOURCE_NOT_FOUND_ERROR` | `404` | `source.sourceId` names no Source of the Entity. `params: { sourceId }`. |
| `SOURCE_NAME_ALREADY_EXISTS_ERROR` | `409` | `source.sourceName` is already the name of a Source of the Entity. `params: { name }`. |
| `SOURCE_FEED_PROVIDER_ACCOUNT_NOT_FOUND_ERROR` | `422` | The Provider doesn't list this `providerAccountId`. `params: { integrationId, providerAccountId }`. |
| `SOURCE_FEED_PROVIDER_ACCOUNT_ALREADY_FED_ERROR` | `409` | Another Feed already reads this Provider Account, in this Entity or another one. `params: { integrationId, providerAccountId }`. |
| `SOURCE_FEED_SOURCE_NOT_EXPENSE_RENDITIONS_ERROR` | `422` | An `expense` Feed names a Source that doesn't hold Expense Renditions. `params: { sourceId }`. |

```bash
curl -X POST "https://api.sintropix.com/api/entities/$ENTITY_ID/source-feeds" \
  -H "x-api-key: $SINTROPIX_API_KEY" \
  -H "x-audit-actor: my-agent" \
  -H "Content-Type: application/json" \
  -d '{
    "id": "e4f5a6b7-c8d9-4e0f-a1b2-c3d4e5f6a7b8",
    "integrationId": "d3e4f5a6-b7c8-4d9e-8f0a-1b2c3d4e5f6a",
    "family": "dte",
    "feedStartDate": "2025-01-01",
    "source": { "sourceName": "Bsale" }
  }'
```

## POST `/source-feeds/:sourceFeedId/sync`

Trigger an on-demand sync of a Source Feed. The response reports how many documents were landed, updated, or skipped. For an `expense` Feed, see [Sync an expense Feed](#sync-an-expense-feed).

**Body**

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `preview` | boolean | No | When `true`, run the full read and landing but roll everything back at the end, so nothing is written and the run is recorded with `outcome: "preview"`. Default `false`. An empty body runs the sync for real. |

**Response:** `{ feed, run }`, the Feed as the listing now shows it and the sync run object that just settled. The documents and Partners the sync landed are not included; read them back through their own endpoints.

- **Status:** `200`.

```bash
curl -X POST "https://api.sintropix.com/api/entities/$ENTITY_ID/source-feeds/$FEED_ID/sync" \
  -H "x-api-key: $SINTROPIX_API_KEY" \
  -H "x-audit-actor: my-agent" \
  -H "Content-Type: application/json" \
  -d '{}'
```

## The sync window

A sync reads the documents dated from the Feed's link date on. How far past the day it runs depends on the provider:

| Provider `kind` | Reads documents dated through |
| --- | --- |
| `bsale`, `wasabil` | One month after the day the sync runs, on the Chilean calendar. This holds for Bsale sales and the Bsale purchase book alike. |
| `sii_mirror` | The end of the current month. The sync reads whole months of the SII registers, up to the current one. See [The current month](#the-current-month). |
| `xpendit` | The day the sync runs. See [Sync an expense Feed](#sync-an-expense-feed). |

A document dated after the day the sync runs lands like any other. For example, a BHE issued on 28 October and dated 31 October lands on the next sync. A Bsale or Wasabil document dated more than a month ahead lands on the first sync within a month of its date. The run's `sweptTo` stays the day the sync ran.

A document dated before the link date doesn't land. The run lists it in `report.ignored` with the reason `issued_before_link_date`. To land it, [move the link date](#patch-/source-feeds/sourcefeedid) earlier.

## Ignored documents

A sync **ignores** a document it reads but the Feed doesn't land. Each ignored document counts in `ignored` on its tie-out line and in the run's `ignoredCount`, and the run lists it in `report.ignored` with its reason. A range the books don't track (a tie-out line with `tracked: false`) counts its documents in `ignored` but doesn't list them one by one.

Each entry in `report.ignored[]`:

| Field | Type | Description |
| --- | --- | --- |
| `externalRef` | string | The document's provider-side id. For an expense, its id at Xpendit. |
| `dteTypeCode` | string \| null | SII document type code. `null` when the provider states no type, and for an expense. |
| `folio` | integer \| null | Document folio, or the expense number for an expense. |
| `issueDate` | string (`YYYY-MM-DD`) \| null | The document's issue date, or the expense's date. |
| `counterpartyRut` | string \| null | RUT of the document's counterparty, or of the person who reported the expense. |
| `counterpartyName` | string \| null | Name of the counterparty, or of the person who reported the expense. |
| `reason` | enum | Why the document didn't land. See below. |

| `reason` | Meaning |
| --- | --- |
| `type_not_stated` | The provider states no type for the document. |
| `type_not_tracked` | The Feed lands no document of this type. |
| `direction_mismatch` | The provider listed the document in the book of the other side: issued instead of received, or the reverse. |
| `issued_before_link_date` | The document is dated before the Feed's link date. See [The sync window](#the-sync-window). |
| `expense_not_approved` | Xpendit hasn't approved the expense yet. Only on an [expense Feed](#sync-an-expense-feed). |
| `expense_kind_not_tracked` | The expense is a `corporate_card` expense, or another kind the Feed doesn't land. Only on an [expense Feed](#sync-an-expense-feed). |

Each sync reads its whole range again, so an ignored document lands on a later sync once its reason no longer holds, for example once Xpendit approves the expense.

`report.ignored` is absent on runs recorded before Sintropix listed ignored documents. Those runs state only `ignoredCount` and the tie-out line counts.

```json
{
  "ignored": [
    {
      "externalRef": "sii:received:33:8812",
      "dteTypeCode": "33",
      "folio": 8812,
      "issueDate": "2026-09-27",
      "counterpartyRut": "76123456-7",
      "counterpartyName": "Distribuidora Andes SpA",
      "reason": "issued_before_link_date"
    }
  ]
}
```

In the app, the run detail shows **Documentos ignorados**. It lists each ignored document with its type, folio, issue date, counterparty, and the reason in words, and you can copy the RUT. For an expense Feed, it shows the expense's date and person instead. A run recorded before the list existed shows no such section.

## Standing and Tax Period

The SII decides two facts of a DTE: its **Standing** (where the SII holds the document) and its **Tax Period** (the F29 / IVA month it belongs to). Both can change after the document lands. A sync lands every document with its Standing and, on every pass, writes the Standing and the Tax Period the provider now states over each DTE it already landed, whether the Invoice is booked or not.

| Standing | Meaning |
| --- | --- |
| `accepted` | The SII holds the document. |
| `pending` | The SII has the document but it isn't final yet. For a received document, you can still claim it. |
| `claimed` | The receiver claimed the document at the SII. |
| `annulment_requested` | Someone asked the SII to annul the document, and the SII hasn't annulled it yet. |
| `annulled` | The document was annulled. |
| `observed` | The SII observed the document. |

The Standing appears as `standing` on the [DTE](/api-reference/sii). A DTE you enter by hand has `standing: null`. You can't set or change the Standing yourself: only a sync writes it.

A sync never changes anything else on a landed document. Your booking, Allocations, and every other fact of the Invoice stay yours. A sync writes the Standing and Tax Period without touching the Invoice or the ledger, so it also updates a booked Invoice and a document dated before the Lock Date. Changes to any other field are reported as `divergences` and not written.

How a sync reads each provider:

| Provider `kind` | Standing | Tax Period |
| --- | --- | --- |
| `sii_mirror`, `dte` Feed | `REGISTRO` and `NO_INCLUIR` are `accepted`, `PENDIENTE` is `pending`, and `RECLAMADO` is `claimed`. | The month of the register that lists the document. When the SII moves a document to another month, the later month wins. |
| `bsale` | A sale annulled in Bsale is `annulled`. A sale Bsale sent and the SII hasn't answered yet is `pending`. A sale the SII rejected is refused with `sii_rejected` and never lands. A purchase canceled in Bsale is `annulled`. Every other document is `accepted`. | Stated for purchases. Bsale states none for sales, so a Tax Period you set on a sale stays. |
| `wasabil` | An emitted document is `accepted`, any other is `pending`. | Not stated, so a Tax Period you set stays. |
| `sii_mirror`, `honorarium` Feed | `N` and `VIG` are `accepted`, `S` and `ANUL` are `annulled`, `V` is `annulment_requested`, and `R` and `U` are `observed`. | The month of the book that lists the document. |

A Tax Period the provider doesn't state never clears the one the DTE holds. A document missing from a provider's answer keeps its Standing.

### Booking and the Standing

A `pending` document lands like an `accepted` one, and is [booked from its vendor's Booking Template](/api-reference/partners#when-an-invoice-is-booked-automatically) when the template applies. You can then match it against the bank as soon as it's paid.

A document that lands `claimed`, `annulment_requested`, or `annulled` is never booked automatically. A booked Invoice whose DTE later reaches one of those Standings stays booked: Sintropix doesn't unbook it or block the change. Instead, it flags an Incompatible Standing.

A document that lands unbooked with one of those Standings, and that you'll never book, stays pending work until you [exclude it from the books](/api-reference/invoices#exclude-an-invoice-from-the-books).

### Incompatible Standing

An Invoice has an **Incompatible Standing** when it's booked and its DTE is `claimed`, `annulment_requested`, or `annulled`: your books count a document the SII doesn't. Sintropix derives it on read and never stores it. It clears as soon as you unbook the Invoice or the Standing changes back.

Find these Invoices in three places:

- `GET /invoices/pages?standing=incompatible` lists them. See [Invoices](/api-reference/invoices#get-/invoices/pages).
- The home dashboard counts them in `incompatibleStandingCount`. See [Home dashboard](/api-reference/reports#home-dashboard).
- In the app, the Invoice panel shows a warning. If you're `staff` in the Entity's Organization, **Estados incompatibles** lists every one, and **Home** counts them under **Necesita acción**. Other Roles see neither the view nor the **Home** row, and their **Necesita acción** total leaves these Invoices out. The two endpoints above work the same for every Role.

Review each one and [unbook](/api-reference/ledger-entries#delete-/api/entities/entityid/ledger/entries/entryid) the Invoice's entry if it no longer belongs in your books.

### Audit and preview

Each write a sync makes to a Standing or a Tax Period appears in the [Audit Trail](/api-reference/audit-trail), credited to the system with the declared actor `source-feed`. The sync run lists each one in `report.updates`, with the value before and after:

```json
{
  "updates": [
    {
      "dteId": "c3d4e5f6-a7b8-4c9d-8e0f-1a2b3c4d5e6f",
      "externalRef": "sii:received:33:5521",
      "dteTypeCode": "33",
      "folio": 5521,
      "fields": [
        { "field": "standing", "landed": "pending", "provider": "accepted" },
        { "field": "taxPeriod", "landed": "2026-08", "provider": "2026-09" }
      ]
    }
  ]
}
```

A sync with `preview: true` lists the updates it would make in `report.updates` and writes none.

## SII Mirror Feeds

A Feed that reads through a `sii_mirror` [Integration](/api-reference/integrations#sii) reads the SII registers of the RUT the Integration connected, month by month, from the link date to the day it runs. It reads that RUT whatever Entity the Feed lands in. Each document it lands names that RUT, with the Entity's name, as the company's side: the issuer of a sale and the receiver of a purchase.

### SII Mirror boletas

The SII states boletas (types `39` and `41`) as one consolidated row per type and month, and lists each boleta later, as it itemizes them. A sync lands each boleta the SII has itemized as its own Invoice. The boletas of the row that are not itemized yet count in `awaiting` on the row's tie-out line and in the run's `awaitingCount`. A later sync lands them once the SII lists them, so the count moves from `awaiting` to `landed`.

A boleta that states the RUT `66666666-6`, or that the Entity issued with no buyer RUT, lands on the final-consumer Partner, named `Consumidor Final` with `taxId` `66666666-6`. A consolidated row that the SII never itemizes counts as `ignored`.

### SII Mirror sales summaries

For the sales types the SII states only as a monthly total (`35`, `38`, `47`, `48`, `105`, `919`, `920`, `922`, and `924`), a sync writes a [Sales Summary](/api-reference/sii#sales-summaries) per type and month and lands it as receivable Invoices on the final-consumer Partner, in the Feed's Source:

- **The first Invoice** lands the SII's figures. Its `documentNumber` names the type and the month, such as `48-2026-09`, and its memo reads `RCV tipo 48 · 2026-09`. It is dated on the last day of the month. Its DTE carries the type, the Tax Period, and the Standing `accepted`, and names the Sales Summary in place of a folio.
- **Before you book it**, a later sync writes the SII's new figures over the Invoice. This holds for any Invoice of the Sales Summary that is neither booked nor [excluded](/api-reference/invoices#exclude-an-invoice-from-the-books).
- **After you book it**, a change the SII makes lands as an adjustment: a new Invoice for the difference, numbered `48-2026-09-2`, `48-2026-09-3`, and so on, with the memo `Ajuste RCV tipo 48 · 2026-09`. When the total drops, the adjustment is a credit note of the same type. Nothing you booked moves, so its Matches and the Lock Date stay as they are.

Book, match, and pay these Invoices like any other receivable. Their DTE can't be written or removed by hand; see [Sales Summary errors](/api-reference/sii#sales-summary-errors). In the app, each of these Invoices says whether it is the original or an adjustment, states the SII's figure, and lists every Invoice of the month with its booking state.

The tie-out line of a total-only type is tracked. Its `count` is the SII's document count. A sync that writes the Sales Summary counts it as `landed`, and a sync that finds the figures unchanged counts it as `skipped`.

### Honorarium Feeds

A Feed with `family: "honorarium"` reads through a `sii_mirror` Integration and lands the Entity's boletas de honorarios from two SII books:

- **BHE recibidas**: the boletas de honorarios electrónicas the Entity receives from the people it pays.
- **BTE emitidas**: the boletas de prestación de servicios de terceros the Entity issues for the people it pays.

Both are payables. Each lands as a `payable` Invoice whose `total` is the net amount the Entity pays, with the Tax Period of the month whose book lists it. Every document lands with its [Standing](#standing-and-tax-period), including annulled ones, and a later sync updates the Standing and the Tax Period.

A sync reads every month of both books from the link date to the day it runs, and states one tie-out line per book and month. It attaches the PDF of each document; honorarium documents have no XML.

### The current month

The mirror may not have read the current month yet, for example in the first hours of a month. A sync then reads the current month, on the Chilean calendar, as empty: it states no tie-out line for it and does not fail. A past month the mirror holds no answer for still fails the sync with `424`, because that is a real gap.

### Recent months

The SII can still change a month for a while after it closes, so the mirror reads its newest months again on every pass. A sync needs the current month, on the Chilean calendar, and the 2 months before it to hold an answer the mirror read in the last 24 hours. If one of them doesn't, the sync fails with `424`.

An older month only needs an answer, of any age. A Feed with an early link date keeps syncing, and an older month lands as the mirror last read it. A past month with no answer at all still fails the sync, whatever its age.

## File attachments

Some providers carry the source files of each document (the PDF and the XML). When a sync runs against such an Integration, after the documents land it also attaches those files to the [Invoice](/api-reference/invoices) of each landed or skipped document, as [Attachments](/api-reference/attachments).

The providers that carry files today:

| Provider `kind` | Documents with files attached |
| --- | --- |
| `sii_mirror` | All issued and received DTEs, except boletas (`39`, `41`), which the SII lists with no files. The SII serves these files only to the legal representative, so add the [legal representative's Clave](/api-reference/integrations#the-legal-representative’s-clave) to the Integration. A [Honorarium Feed](#honorarium-feeds) attaches the PDF of each BHE and BTE. |
| `bsale` | Sales documents. Purchases keep their PDF and XML as evidence lines on the Source Feed, because the Bsale purchase `urlPdf` answers HTML rather than a PDF. |
| `wasabil` | Issued and received documents. |
| `xpendit` | Each expense's receipt and its additional file, when it has one. See [Expense files](#expense-files). |

Other Integration kinds (for example `mercadopago`, `mercadolibre`) report no files and this section does not apply.

**Gap rule.** The sync attaches only the kinds the Invoice does not already have. Any PDF already on the Invoice satisfies the PDF slot, whether an earlier sync or a user attached it. Same for XML. If a user later deletes a file that a sync attached, the next sync attaches it again.

**Cap.** A sync you trigger with `POST /source-feeds/:sourceFeedId/sync` attaches at most 200 files, and a scheduled sync at most 1000, newest documents first. The rest are counted in `deferred` and picked up on the next sync.

**Filename.** Attached files are named `DTE-<dteTypeCode>-<folio>-<issuerRut>.<pdf|xml>`, for example `DTE-46-10-78404916-7.xml`.

**Preview.** A sync with `preview: true` reads no bytes. Its `report.files.attached` counts the files the sync would attach.

**Failures never fail the sync.** A file that could not be read or attached is listed in `failed[]` with a `reason`, and the next sync retries it.

### File report shape

`report.files` on the sync run object:

| Field | Type | Description |
| --- | --- | --- |
| `attached` | integer | Files the sync added to an Invoice. |
| `held` | integer | Files the Invoice already had (a matching PDF or XML was already attached). |
| `missing` | integer | Files the provider does not hold. |
| `deferred` | integer | Files past the per-sync cap. The next sync attaches them. |
| `failed` | array | Files the sync could not attach. See below. |

Each entry in `failed[]`:

| Field | Type | Description |
| --- | --- | --- |
| `externalRef` | string | The document's provider-side id. |
| `dteTypeCode` | string \| null | SII document type code. `null` for an expense file. |
| `folio` | integer \| null | Document folio, or the expense number for an expense file. |
| `kind` | `pdf` \| `xml` \| `receipt` \| `additional_receipt` | Which file failed. `receipt` and `additional_receipt` are the files of an expense. |
| `reason` | enum | One of `not_found`, `unavailable`, `integrity_failure`, `too_large`, `attach_failed`. |
| `detail` | string | Operator-facing error code. |

```json
{
  "report": {
    "tieOutLines": [],
    "rejected": [],
    "divergences": [],
    "updates": [],
    "files": {
      "attached": 24,
      "held": 316,
      "missing": 2,
      "deferred": 0,
      "failed": [
        {
          "externalRef": "sii:issued:33:1042",
          "dteTypeCode": "33",
          "folio": 1042,
          "kind": "pdf",
          "reason": "integrity_failure",
          "detail": "sha256_mismatch"
        }
      ]
    }
  }
}
```

## Expense Feeds

An `expense` Feed routes one **Provider Account** of an expense tool to a Source of an Entity that [holds Expense Renditions](/api-reference/sources#sources-that-hold-expense-renditions). A Provider Account is one account inside the external account of an Integration. Today only [Xpendit](/api-reference/integrations#xpendit) feeds expenses, and its Provider Accounts are the Subsidiaries of the enterprise.

The routing rules:

- **One Provider Account feeds one Entity.** A Subsidiary that another Feed already reads answers `409` with `SOURCE_FEED_PROVIDER_ACCOUNT_ALREADY_FED_ERROR`.
- **An Entity holds one `expense` Feed**, like every other family. A second one answers `409` with `SOURCE_FEED_FAMILY_ALREADY_FED_ERROR`.
- **The Source holds Expense Renditions.** An existing Source without the mark answers `422` with `SOURCE_FEED_SOURCE_NOT_EXPENSE_RENDITIONS_ERROR`. A Source the Feed creates holds them. While the Feed lives, you can't unmark its Source: Sintropix refuses with `409` and `SOURCE_PINNED_ERROR`.
- **The Provider lists the account.** List the Provider Accounts with [`GET /integrations/:integrationId/provider-accounts`](/api-reference/integrations#get-/integrations/integrationid/provider-accounts). An id the Provider doesn't list answers `422` with `SOURCE_FEED_PROVIDER_ACCOUNT_NOT_FOUND_ERROR`.

In the app, open the Xpendit Integration's panel. Its feed step shows one row per Subsidiary that no Feed reads yet. For each one, pick a Source that holds Expense Renditions, or create one, and its Link Date. A routed Subsidiary shows **Rendiciones**, the **Cuenta del proveedor**, the Source, and the Link Date, with **Sincronizar** and **Vista previa**.

```bash
curl -X POST "https://api.sintropix.com/api/entities/$ENTITY_ID/source-feeds" \
  -H "x-api-key: $SINTROPIX_API_KEY" \
  -H "x-audit-actor: my-agent" \
  -H "x-audit-reason: Route the Acme Chile subsidiary to the renditions Source" \
  -H "Content-Type: application/json" \
  -d '{
    "id": "b1c2d3e4-f5a6-4b7c-8d9e-0f1a2b3c4d5e",
    "integrationId": "7c8d9e0f-1a2b-4c3d-8e4f-5a6b7c8d9e0f",
    "family": "expense",
    "providerAccountId": "4821",
    "feedStartDate": "2026-10-01",
    "source": { "sourceName": "Rendiciones Xpendit" }
  }'
```

### Sync an expense Feed

A sync of an `expense` Feed lands each expense the tool approved as an [Expense Claim](/api-reference/expense-claims) that the Feed approves in the same act. Approving books it as an [Expense Rendition](/api-reference/sources#sources-that-hold-expense-renditions) in the Feed's Source. Sintropix syncs it every 4 hours with the other Feeds, and you can [sync it on demand](#post-/source-feeds/sourcefeedid/sync). In the app, click **Sincronizar** or **Vista previa** on the Subsidiary's line in the Integration's panel.

Before the first sync, set the Entity's [booking setting](/api-reference/expense-claims#before-you-submit-claims). The Feed books with its **Rendición por pagar** account and its supplier payable account. Without the setting, the sync fails with `409` and `EXPENSE_CLAIM_SETTING_NOT_SET_ERROR` and lands nothing. The Feed doesn't need the Approver: Xpendit already approved the expense.

**What a sync reads.** It reads the expenses created in each month from the Link Date to today, one month at a time. Each month is a tie-out line with `range.month` set, and its `count` is the number of expenses Xpendit states for that month.

**What lands.** An expense lands when Xpendit's `state` is `approved`, `accounted`, or `paid`, and its `expenseType` is `reimbursement`, `one_time_fund`, or `recurrent_fund`. Every other expense counts as `ignored` and is listed in `report.ignored`: a `corporate_card` or `other` expense with `expense_kind_not_tracked`, whether Xpendit approved it or not, and any other expense Xpendit hasn't approved with `expense_not_approved`. See [Ignored documents](#ignored-documents). An expense whose claim already exists counts as `skipped`.

Each landed claim gets these values:

| Claim field | Value |
| --- | --- |
| `id` | The expense's id at Xpendit, so a later sync finds it. |
| `partnerId` | The person who reported the expense. Sintropix finds or creates the Partner by the person's RUT, in any format. A person with no valid RUT is found or created by name. |
| `expenseDate` | The expense's date. |
| `amount` | The amount the Subsidiary reimburses, in its own currency. |
| `memo` | The merchant and the description, such as `COPEC · Combustible visita cliente`. Without either, the category's name. |
| `receiptKind` | `factura` when the Entity holds a DTE of type `33` or `34` with the merchant's RUT and folio, or when Xpendit names the document a factura and states a valid merchant RUT and a numeric folio. `boleta` otherwise. |
| `expenseCategoryId` | The Entity's category for the expense's Xpendit category. See [Categories](#expense-categories-from-xpendit). |

The Expense Rendition is booked like any [approved claim](/api-reference/expense-claims#what-approving-books), but it lands in the Feed's Source. It carries what Xpendit states of the expense as Additional Information: the expense number, the merchant and its RUT, the folio, the document type, the amount paid, the fund, the cost center, and the category.

**What a sync refuses.** An expense that can't land counts as `rejected` and is listed in `report.rejected` with one of these reasons:

| `reason` | Meaning | `detail` |
| --- | --- | --- |
| `currency_mismatch` | The expense isn't in the Entity's functional currency. | The expense's currency |
| `total_off_scale` | The amount is zero, negative, or doesn't fit the currency. | The amount |
| `person_unknown` | The expense names no person. | The person's name, when present |
| `expense_category_unassigned` | The expense's category has no expense account yet. | The category's name |
| `document_invalid` | Booking the claim failed. | The error code |

A rejected expense isn't stored, so a later sync tries it again.

#### Expense categories from Xpendit

The sync gives each Xpendit category an [Expense Category](/api-reference/expense-claims#expense-categories) of the Entity:

1. The category the Feed created for it on an earlier sync, even if you renamed it.
2. Else the Entity's own category with the same name. The Feed takes it over, so it still finds it once you rename it.
3. Else a new category with that name and no expense account. Its `sourceFeedId` is the Feed, and its `providerCategoryId` is Xpendit's category id.

An expense whose category has no expense account is rejected with `expense_category_unassigned`. Assign the account in **Configuración → Rendiciones** or with [`PATCH /expense-categories/:expenseCategoryId`](/api-reference/expense-claims#patch-/expense-categories/expensecategoryid). The next sync lands the expense.

#### Changed expenses

A sync never rewrites a claim it already landed. When the `amount` or the `expenseDate` of a landed expense changes in Xpendit, the expense counts as `skipped` and appears in `report.expenseDivergences`:

```json
{
  "expenseDivergences": [
    {
      "expenseClaimId": "3f2a1b0c-9d8e-4f7a-8b6c-5d4e3f2a1b0c",
      "externalRef": "3f2a1b0c-9d8e-4f7a-8b6c-5d4e3f2a1b0c",
      "folio": 1042,
      "fields": [
        { "field": "amount", "landed": "25000", "provider": "27500" }
      ]
    }
  ]
}
```

`folio` is the expense number. `landed` and `provider` are text: the amount in minor units of the Entity's functional currency, or the date as `YYYY-MM-DD`. Review each change and correct the Expense Rendition yourself when it no longer matches the expense.

#### Expense files

An Xpendit expense carries a receipt and, at times, an additional file. A sync attaches each one to the Expense Rendition as an [Attachment](/api-reference/attachments), once per slot: `receipt` and `additional_receipt`. It attaches them for the expenses it lands and for the ones it skips, so a file that failed on one sync is tried again on the next. The counts appear in `report.files`, and a failed file appears in `failed[]` with its `kind`.

#### Preview

A sync with `preview: true` reads and lands every expense, then rolls everything back. It reports what a real sync would land, skip, ignore, and reject, and writes no claim, category, Partner, or file.

The run detail in the app lists the month ranges, the rejected expenses, the ignored expenses, the changed expenses, and the files that failed.

## DTE references

A sync also links each DTE to the DTEs it references, for example a nota de crédito to the factura it credits. The links appear in `statedDteReferences` and `receivedDteReferences` on [`GET /sii/dte/:dteId`](/api-reference/sii), with the SII `referenceCode` (`1` voids, `2` corrects text, `3` corrects amounts) when the document states one.

Sintropix reads the references from two places:

- **The provider's data.** `sii_mirror` and `wasabil` state the references of each document. `bsale` states none.
- **The attached XML.** When a sync attaches a DTE's XML (see [File attachments](#file-attachments)), Sintropix reads the `<Referencia>` blocks of that XML, whatever the provider. An XML whose type and folio do not match the DTE is not read.

A reference is linked only when its target is already in the Entity's books: a DTE of the same issuer, with the stated type and folio. A target that is not there yet is not linked. For a reference the provider states, a sync that runs after the target lands links it, because every sync reads its whole window again. A reference stated only in the XML is read once, when the sync attaches the XML; to link it later, add it with [`POST /sii/dte/:dteId/references`](/api-reference/sii). A stated code fills a reference that has no code, but never replaces a code the reference already has. A sync never removes a reference.

## Status codes

| Status | Meaning |
| --- | --- |
| `200` | Success on `GET`, `PATCH`, `DELETE`, `POST /sync`. |
| `201` | Source Feed created. |
| `400` | Validation error, or missing `x-audit-actor` on a key-authenticated mutation. |
| `404` | Entity, Source Feed (`SOURCE_FEED_NOT_FOUND_ERROR`), Source (`SOURCE_NOT_FOUND_ERROR`), or Integration (`INTEGRATION_NOT_FOUND_ERROR`) not found. |
| `409` | The Feed id already exists (`SOURCE_FEED_ALREADY_EXISTS_ERROR`), the Entity already has a Feed of the family (`SOURCE_FEED_FAMILY_ALREADY_FED_ERROR`), the Source already has a Feed (`SOURCE_FEED_SOURCE_ALREADY_FED_ERROR`), the new Source's name is taken (`SOURCE_NAME_ALREADY_EXISTS_ERROR`), or another Feed already reads the Provider Account (`SOURCE_FEED_PROVIDER_ACCOUNT_ALREADY_FED_ERROR`). On a sync: the provider's stated count and the count read disagree (`SOURCE_FEED_SYNC_TIE_OUT_MISMATCH_ERROR`), or an `expense` Feed's Entity has no booking setting (`EXPENSE_CLAIM_SETTING_NOT_SET_ERROR`). |
| `422` | The Integration's provider doesn't feed the family (`SOURCE_FEED_FAMILY_NOT_FED_ERROR`), the Provider doesn't list the Provider Account (`SOURCE_FEED_PROVIDER_ACCOUNT_NOT_FOUND_ERROR`), or an `expense` Feed names a Source that doesn't hold Expense Renditions (`SOURCE_FEED_SOURCE_NOT_EXPENSE_RENDITIONS_ERROR`). |
| `424` | The provider refused the sync (`SOURCE_FEED_SYNC_PROVIDER_FAULT_ERROR`). See [Provider refusals](/api-reference/overview#provider-refusals). |
