Webhooks let you receive real-time HTTP notifications whenever a meaningful financial event occurs in Sintropix — a new transaction arrives, a reconciliation match is confirmed, a month-end close is completed, or an integration loses its connection. Instead of polling the API, your system receives a push notification the moment the event happens, enabling you to build reactive workflows, trigger downstream automations, and keep external systems in sync without delay.

Managing webhooks requires the `write:webhooks` scope. Reading webhook registrations requires `read:entities`.

---

## POST /webhooks

Register a new webhook endpoint to receive event notifications.

```bash
curl -X POST https://api.sintropix.com/v1/webhooks \
  -H "Authorization: Bearer sk_live_YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "url": "https://yourapp.com/webhooks/sintropix",
    "events": ["transaction.reconciled", "close.completed"],
    "entity_id": "ent_def456",
    "description": "Reconciliation alerts for Chile entity"
  }'
```

### Request Body

<ParamField body="url" type="string" required>
  The HTTPS endpoint where Sintropix will `POST` event payloads. Must use `https://` — HTTP endpoints are not accepted.
</ParamField>

<ParamField body="events" type="array" required>
  Array of event type strings to subscribe to. See the [Event Types](#event-types) table below. Pass `["*"]` to subscribe to all events.
</ParamField>

<ParamField body="entity_id" type="string">
  Scope this webhook to a specific entity. Omit to receive events from all entities in your organization.
</ParamField>

<ParamField body="description" type="string">
  Optional human-readable label for this webhook, visible in the Sintropix dashboard under **Settings → Webhooks**.
</ParamField>

### Response Fields

<ResponseField name="webhook_id" type="string">
  Unique identifier for the registered webhook endpoint (e.g., `wh_jkl012`). Use this ID to delete the webhook later.
</ResponseField>

<ResponseField name="url" type="string">
  The HTTPS endpoint URL where Sintropix will deliver event payloads.
</ResponseField>

<ResponseField name="events" type="array">
  The list of event type strings this webhook is subscribed to.
</ResponseField>

<ResponseField name="entity_id" type="string">
  The entity scope for this webhook, or `null` if the webhook receives events from all entities.
</ResponseField>

<ResponseField name="status" type="string">
  Current status of the webhook. `active` means Sintropix is actively delivering events to this endpoint.
</ResponseField>

<ResponseField name="created_at" type="string">
  ISO 8601 timestamp of when the webhook was registered.
</ResponseField>

### Example Response

```json
{
  "data": {
    "webhook_id": "wh_jkl012",
    "url": "https://yourapp.com/webhooks/sintropix",
    "events": ["transaction.reconciled", "close.completed"],
    "entity_id": "ent_def456",
    "status": "active",
    "created_at": "2025-01-15T14:00:00Z"
  },
  "meta": {
    "request_id": "req_1aYsQ4pItX1bD6gT",
    "timestamp": "2025-01-15T14:00:00Z"
  }
}
```

## Event Types

Subscribe to any combination of the following event types:

| Event | Description |
|-------|-------------|
| `transaction.created` | A new transaction was imported from a connected integration or created via the API. |
| `transaction.reconciled` | A transaction was successfully matched to an accounting document. |
| `transaction.needs_review` | A transaction was flagged for human review — a likely match was found but confidence is below the auto-approval threshold. |
| `close.checklist_updated` | The month-end close checklist completion percentage changed (e.g., a task was marked complete). |
| `close.completed` | The month-end close was fully approved by the finance team. |
| `integration.disconnected` | A connected integration (bank, payroll, CRM, etc.) lost its connection and requires re-authentication. |
| `report.generated` | An asynchronous report generation job completed and the report is ready to retrieve. |

## Webhook Payload

Every event notification is delivered as a `POST` request to your registered URL with the following JSON body:

```json
{
  "event": "transaction.reconciled",
  "timestamp": "2025-01-15T10:30:00Z",
  "entity_id": "ent_abc123",
  "data": {
    "transaction_id": "txn_xyz789",
    "match_id": "match_def456",
    "matched_at": "2025-01-15T10:30:00Z"
  }
}
```

The `data` object structure varies by event type. All payloads include the top-level `event`, `timestamp`, and `entity_id` fields.

Your endpoint must return a `2xx` HTTP status code within **10 seconds** to acknowledge receipt. If your endpoint times out or returns a non-`2xx` status, Sintropix treats the delivery as failed and schedules a retry.

<Note>
  Sintropix retries failed webhook deliveries up to **5 times** using exponential backoff: 1 minute, 5 minutes, 30 minutes, 2 hours, and 8 hours after the initial failure. If all five retries fail, the delivery is marked as permanently failed and you can inspect it in **Settings → Webhooks → Delivery Log**.
</Note>

## Verifying Webhook Signatures

Every webhook request includes an `X-Sintropix-Signature` header. This is an HMAC-SHA256 signature of the raw request body, computed using your **webhook secret** (displayed when you create the webhook). Always verify this signature before processing a payload to ensure it genuinely originated from Sintropix.

<Tabs>
  <Tab title="Python">
    ```python
    import hmac
    import hashlib
    import os

    def verify_signature(payload_body: bytes, signature_header: str) -> bool:
        webhook_secret = os.environ["SINTROPIX_WEBHOOK_SECRET"].encode()
        expected = hmac.new(webhook_secret, payload_body, hashlib.sha256).hexdigest()
        return hmac.compare_digest(expected, signature_header)

    # In your request handler:
    # raw_body = request.body  (bytes, before any JSON parsing)
    # signature = request.headers.get("X-Sintropix-Signature")
    # if not verify_signature(raw_body, signature):
    #     return 401
    ```
  </Tab>
  <Tab title="JavaScript / Node.js">
    ```javascript
    const crypto = require('crypto');

    function verifySignature(rawBody, signatureHeader) {
      const secret = process.env.SINTROPIX_WEBHOOK_SECRET;
      const expected = crypto
        .createHmac('sha256', secret)
        .update(rawBody)          // rawBody must be a Buffer or string, not parsed JSON
        .digest('hex');
      return crypto.timingSafeEqual(
        Buffer.from(expected),
        Buffer.from(signatureHeader)
      );
    }

    // Express example:
    // app.post('/webhooks/sintropix', express.raw({ type: 'application/json' }), (req, res) => {
    //   if (!verifySignature(req.body, req.headers['x-sintropix-signature'])) {
    //     return res.sendStatus(401);
    //   }
    //   const event = JSON.parse(req.body);
    //   // handle event...
    //   res.sendStatus(200);
    // });
    ```
  </Tab>
</Tabs>

<Warning>
  Always use a timing-safe comparison function (`hmac.compare_digest` in Python, `crypto.timingSafeEqual` in Node.js) when verifying signatures. Standard string equality (`==`) is vulnerable to timing attacks that could allow a bad actor to forge valid signatures.
</Warning>

## GET /webhooks

List all webhook endpoints registered in your organization.

```bash
curl https://api.sintropix.com/v1/webhooks \
  -H "Authorization: Bearer sk_live_YOUR_API_KEY"
```

The response is a paginated list of webhook objects, each containing `webhook_id`, `url`, `events`, `entity_id`, `status`, and `created_at`.

## DELETE /webhooks/{webhook_id}

Delete a registered webhook endpoint. Sintropix will immediately stop delivering events to that URL.

```bash
curl -X DELETE https://api.sintropix.com/v1/webhooks/wh_jkl012 \
  -H "Authorization: Bearer sk_live_YOUR_API_KEY"
```

A successful deletion returns `200 OK` with an empty `data` object:

```json
{
  "data": {},
  "meta": {
    "request_id": "req_3cZtR5qJuY2eE7hU",
    "timestamp": "2025-01-15T14:30:00Z"
  }
}
```

<Note>
  Deleting a webhook does not retroactively cancel in-flight deliveries or pending retries. Any events already queued for delivery to that endpoint before the deletion will still attempt delivery.
</Note>
